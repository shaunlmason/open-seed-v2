# os-465e356e — Phase 12 item 1: the compromised-actor drill, the release gate

Build plan Phase 12 item 1. A red-team harness plays the charter's §I.2
adversary against a fixture deployment in **enforced** mode and asserts the
invariant's ceiling clause by clause. The charter calls this drill "the
architecture's definition of done"; the build plan calls it the release gate
and requires it green in CI from here on, and promotion (§5) requires it.

## What the tree actually shows

**The enforced self-hosted hook ships, and it guards one ref.**
`next/cmd/seed-admit` is the charter's reference deployment ("a git
server-side receive hook on the ledger ref"), landed by Phase 2 items 3 and 5
(#94, #99): stateless by construction, importing the same `internal/admit`
rule set the client runs and selecting its share by exclusion, refusing a
deletion, a non-fast-forward update, a tree outside the ledger layout, a
stream that fails verification from genesis, a rewrite of the admitted
prefix, and any new record an admission rule refuses. `drill_test.go`
installs it on a bare remote and already runs the raw-git adversary per
posture and kill-and-replace. An earlier revision of this plan said no hook
existed and proposed a second one; that premise was false, and a second
hook would have given the release gate a boundary deployments do not use
while leaving two security-critical implementations free to drift. The
drill's boundary is `seed-admit`, extended where the ceiling needs more than
it enforces today.

**What it enforces today is the ledger half of the ceiling, and nothing of
the code half.** Every update to a ref other than the guarded one passes
through untouched — `TestHookStdinContractAndRefOverride` pins "non-guarded
refs must pass without repo access". Nothing on the server identifies who
is pushing, and Seed's submission binds `{contract, head, diff_sha256}`
rather than a branch ([`verdicts.md`](../next/spec/verdicts.md)), so "its
own authorized code branches" (charter §II.2) names nothing the tree
defines. Against this fixture a compromised credential pushes the default
branch, another actor's branch, a tag, and a commit rewriting the check
pipeline, and every push lands. The mode fixtures push to unhooked bare
remotes, so the honest loop has never been driven through the hook either.
Three of the twelve ceiling clauses ("modify only its authorized code
surface", "alter gates" on the code side, "rewrite history" on the code
side) therefore have no boundary to assert against, and a drill that
exempted every non-ledger ref would report them green by never asking.

**The adversary's other powers are already played, in process.** The
dispatcher's injection suite ([`lanes.md`](../next/spec/lanes.md)) derives
what a persuaded lane can do from `admit.Affordances`; the curator poisoning
drill ([`curation.md`](../next/spec/curation.md)) scripts each poison to a
promotion attempt and asserts it fails at both ends; the trajectory-prefix
harness ([`trajectories.md`](../next/spec/trajectories.md)) replays recorded
decisions. Each drives `admit.Check` directly, so each proves what admission
refuses and none proves what a *push* is refused with a valid key, a valid
credential and raw git. That narrower, harder question is §I.2's, and it is
this card's subject.

**The posture declaration is strict and small.** `internal/posture` reads
`{"posture": "<name>"}` and refuses unknown fields; `seed doctor` reads it
from `seed.json`. The charter says the protected surface is "enumerated in
config"; no Seed config enumerates it yet (Phase 12 item 4's preseed is
where the declaration grows), and the fixture's hook needs the list from
somewhere stateless.

## Design decisions (binding for this task)

**D1. The drill's boundary is `seed-admit`, extended; never a second hook.**
The hook gains a **code-ref half** beside its ledger half. For every update
line naming a ref other than the guarded ledger ref, it decides from two
things it already has or the transport asserts: the ledger at the guarded
ref's current tip (the keyring's standing and the lifecycle fold's claim
holders, derived exactly as the ledger half derives them — stateless, from
the repository it guards) and the pusher's identity. The rules, in the
reference deployment's own terms:

- *The default branch* (the bare repository's `HEAD` symref, so no
  configuration names it): a fast-forward by a credential whose actor holds
  operator standing (a governance root, or an `operator` grant) is admitted;
  a force-update or deletion is refused for everyone.
- *A contract branch* `refs/heads/seed/<contract>`: any update — create,
  fast-forward, force-update, delete — by the actor holding the **active**
  claim on `<contract>` is admitted; that is the work branch the charter's
  "its own authorized code branches" names, and it is authorized by the
  claim, so it closes when the window closes. Anyone else is refused.
- *Tags*: creation by operator standing only; an update or deletion of an
  existing tag is refused for everyone (§II.14, "immutable release tags").
- *Operator standing* may otherwise create or fast-forward any ref; an
  agent credential may touch nothing else; a push whose transport asserts no
  identity is refused on every code ref.
- *The protected surface*: a push by a credential without operator standing
  whose new commits touch a protected path is refused on any ref, which is
  §II.14's "write-denied to every agent key whose work it gates" made a
  property of the remote. The list is read from the deployment declaration
  at the default branch's **current** tip, never from the pushed commits (or
  the attacker unprotects by rewriting the list in the same push), and the
  declaration's own path is protected by construction.

The ledger half is unchanged. Refused: teaching either half a rule the
other derivation lacks; consulting anything the hook cannot rebuild from a
clone; a code-ref decision that reads the pushed tree for its inputs.

**D2. The pusher's identity is the transport's assertion, and the fixture
says so.** The hook reads `SEED_PUSHER`, the actor's key fingerprint, from
its environment. In the reference deployment the ssh forced command sets it
from the authenticated key, which the fixed defaults already make the
actor's signing key (OpenSSH ed25519 keys are accepted so operators reuse
them), so the credential and the key are one object and the fingerprint is
derived, not configured. In the fixture the transport is a filesystem path,
and the harness sets `SEED_PUSHER` in the adversary's environment when it
hands out the credential. Forging that variable is stealing another actor's
credential, which §I.2 places outside the adversary ("cannot compromise
another actor's key or the trusted git infrastructure"); the corpus never
varies it, and one characterization drill pins what a forged identity buys
(that actor's contract branch and nothing on the ledger, whose half is
signature-bound). Refused: an identity read from the pushed objects, a
commit author, or anything the pusher controls.

**D3. The adversary is a process constrained to git transport.** The harness
holds a real enrolled implementer key with a `claim` grant, a real
credential (its `SEED_PUSHER` identity, and read/write access to the remote
over `git push`), and runs `git` directly. It never calls the honest CLI to
perform an attack: an attack that goes through `seed claim take` proves the
client refuses, which is not the claim. It never writes the bare
repository's filesystem directly, because a writer inside the server is the
compromised infrastructure §I.2 excludes; the harness refuses to construct
one. Forged events are signed with the compromised key and pushed with `git
push`, so the only thing between the attacker and the ref is the hook, and
the drill states that as the fixture's contract.

**D4. The corpus is declarative and derived from the ceiling.** §I.2's
ceiling is eight prohibitions ("cannot claim unauthorized work, approve
itself, rewrite history, alter gates, impersonate another actor, exceed its
lease, cause an invalid state transition to enter authoritative history"
and, from §9, "spend beyond reservation") and four permissions ("can spend
only its reserved budget; modify only its authorized code surface; produce
signed lies attributed to itself; submit work for independent
verification"). `next/internal/redteam/testdata/ceiling.json` names all
twelve clauses with the charter's own words and, per clause, the Seed
vocabulary it lands in: "lease" is the claim window, since Seed holds no
lease ([`observations.md`](../next/spec/observations.md)), so over-lease is
an act citing a fence that is no longer active and a contract-branch push
after the window closed; "alter gates" has a ledger side (a grant to
itself, a lifted halt, an approval of its own plan, a promoted lesson, a
re-specified acceptance, a seal from a claim holder) and a code side (the
default branch; a protected path); "rewrite history" has both sides too.
The corpus names, per attack, the clause it attacks, the side, and the
refusal it must meet. Coverage is derived from the clause list and pinned
**both ways**: a clause with no attack fails, an attack naming no clause
fails, and a two-sided clause with one side missing fails.

**D5. The permissions and their negatives are asserted together.** A
harness that only asserts refusals passes trivially against a remote that
refuses everything, and a harness that asserts only "its own branch is
writable" cannot see that every other branch was too. Each permission is an
admitted push under the same fixture and key: the attacker spends inside
its reservation, pushes its own contract branch during its window, appends
a signed lie attributed to itself (a dead end recording something false,
which is evidence, not conclusion), and submits for verification, with a
verifier key's verdict landing over the submission. Each permission's
*boundary* is a refused push beside it: another actor's contract branch,
the default branch, a new tag, a commit touching a protected path on its
own branch, the same branch after `claim.released`, and a reservation
beyond the class. The drill fails if any admitted push is refused or any
refused push lands.

**D6. What the drill proves is bounded, and the bound is stated.** The hook
proves the enforced-self-hosted posture. Cooperative mode is out of scope
by construction (the charter already names its consequence), and
enforced-forge-hosted is Phase 12 item 2's admission service; the drill's
spec says so, and the residual table carries "the drill's fixture is one
posture". Refused: a drill that runs in cooperative mode and reports green,
which would assert the opposite of what the charter says holds there.

**D7. Residuals are named, not hidden.** Where the adversary succeeds within
the ceiling, the success is a named residual with why, what it can inflict
and what stands in the way, each pinned by a characterization drill
asserting the attack IS admitted — the shape both landed suites use. The
starting set: the signed lie (attribution is not trust); self-directed
budget exhaustion inside its own reservation; refusal-flooding the remote
(denial of progress, not of authority); test content outside the protected
surface on its own branch (the charter's own named residual, with
diff-vs-plan review and sealed checks as the mitigations); the
credential-to-identity binding being the transport's (D2); and the
one-posture bound (D6).

**D8. The gate is `make check`, and CI runs it already.** The drill is a Go
test under `next/`, so the existing `check` job runs it; no workflow file
changes. The build plan's "runs in CI from here on" is met by the drill
living where `make check` looks, and by `lanes.md` recording III.O's drill
row as met. Refused: a separate workflow job, which would let the release
gate be skipped by a path the rest of the suite does not take.

**D9. Revocation's reap arm is a follow-up card, not this one.** The Phase
10 exit record routes charter III.E row 8's reap arm ("revocation … reaps
its claims") to this item: today the maintenance reap needs an interrupt
answered by silence, and a revoked holder's `no_data` stream has no reap
path at all, so a revoked key's open claims stand until someone notices.
That is a lifecycle change (a reap corroborated by the revocation record
itself, with a packet, so the work is re-offered) with its own boundary
rule, its own maintenance step and its own drills, and it is carded
separately as os-32d06c65 rather than absorbed here: the release gate
should land as a drill over the boundary as it stands, and a card that
changed the lifecycle and drilled the ceiling in one diff would be judged
on neither. What this drill asserts about revocation is today's
consequence, in both halves: a revoked key's proposals refuse at the
push, and its contract branch closes with its standing (D1's holder rule
reads the keyring, so a revoked holder is no holder). The reap arm is
named in `redteam.md`'s residual table with its card, and the follow-up's
own drill extends the corpus when it lands.

## Acceptance Criteria

**Boundary set (new, shown working):**

1. **The code-ref half enforces.** Under the same installed hook: the
   default branch fast-forwards for operator standing and refuses for an
   agent credential, and its force-update and deletion refuse for both; a
   contract branch admits every update from its active claim holder and
   refuses any other identity, and refuses the holder after the window
   closes; a tag is created by operator standing only and never updated or
   deleted; a push touching a protected path refuses for an agent
   credential on its own branch, with the declaration's own path protected
   when the list is empty; a push asserting no identity refuses on every
   code ref; a ledger-ref push is judged exactly as before. Every refusal
   carries the boundary's own reason on stderr and moves no ref.
2. **The ceiling, clause by clause.** Every one of the eight prohibitions
   has at least one attack on each side D4 gives it, run by the adversary
   with its own key and raw git against the enforced fixture, and each is
   refused at the push: an unauthorized claim, a self-approval, a history
   rewrite (ledger and code), a gate modification (ledger and code), an
   impersonation, an over-lease act (ledger and code), an invalid
   transition, and a spend beyond reservation.
3. **The permissions and their negatives.** Each of the four is an
   admitted push under the same fixture and key, and each of D5's negatives
   is a refused push beside it.
4. **Coverage both ways.** A clause with no attack fails the drill; a
   two-sided clause with one side missing fails; an attack naming no clause
   fails; an empty corpus fails.
5. **One derivation.** The ledger-side corpus run through `admit.Check` in
   process and through the hook over a real push yields the same verdict
   for every entry.
6. **The residuals** are named in `residuals.json` with why, the
   inflictable consequence and what stands in the way, each pinned by a
   drill asserting the attack is admitted; an unnamed admitted attack
   fails, and a named one the corpus cannot reach fails as stale.
7. **Mutation evidence.** Each must fail a drill: the hook admitting on
   refusal; the hook checking only the first pushed commit; the hook
   allowing a force-update or a deletion of the ledger ref; the hook
   reading the new tip instead of the old for its ledger context; a code
   ref admitted with no asserted identity; the claim-holder check dropped;
   the default-branch rule dropped; tag immutability dropped; the
   protected list read from the pushed commit instead of the default
   branch's tip; the declaration path not protected by construction; the
   ceiling read from the corpus instead of the charter table; the
   permissions arm dropped; a negative dropped; a residual dropped; the
   drill running in cooperative mode; the harness writing the bare
   repository directly.
8. `make check` green with coverage measured **cold**, at least three
   readings above the gate, and the suites pass **unprivileged**.

**Retention set (existing, shown unharmed):**

- The ledger half is unchanged: every existing `seed-admit` drill (the raw
  adversary per posture, kill-and-replace, rotation, the compromised-key
  cut, the enrollment chain, tree shape, stdin contract) passes as before,
  except the one line that pinned non-guarded refs passing, which is
  amended deliberately and named in the task PR.
- The CLI's remote path is unchanged: `gitref`'s optimistic retry, the
  refusal mapping (`remote_rejected`, exit 11) and every existing remote
  drill pass as before; the honest fixtures that push to unhooked bare
  remotes keep pushing, the mode fixtures included.
- `internal/admit` is untouched; no new verb, transition row, capability,
  exit code or protocol version; every pre-existing chain verifies byte for
  byte; the projections' builds are byte-identical on chains this card does
  not create; a declaration without `protected` loads as before and an
  unknown field still refuses.
- The three landed adversarial suites are untouched and still green.
