# Plan: next Phase 5.5 — the falsifiable-plan lint and plan-gating (os-16c1d142)

Authority: docs/next-build-plan.md Phase 5 item 5: "Plans:
falsifiable-plan lint (boundary set, retention set, commands, diff
shape); plan-gating rule above the trivial tier." Charter (SEED-NEXT.md
Part II §6) "Plans as falsifiable change contracts": above the trivial
tier, claiming an unplanned contract authorizes planning only; a plan
is a file merged through its own single-file PR; it MUST name the
boundary set, the retention set, the validation commands for both, and
the expected shape of the diff; "A plan without a retention check does
not lint"; "Plan PRs and implementation PRs are structurally disjoint,
enforced by CI classification." Conformance III.F: "Plans are
falsifiable: boundary set, retention set, validation commands for
both, expected diff shape; missing retention fails lint; plan and
implementation PRs are structurally disjoint." Catalog vocabulary:
`plan.proposed`, `plan.approved` ("observation of the plan PR merge")
— the only two `plan.*` verbs; no others are invented here.

## Design decisions (binding for this task)

- **The gate bites at `submission.made`, not `claim.taken`.** The
  charter's own sentence says claiming an unplanned contract is
  *allowed* and "authorizes planning only" — planning work needs the
  claim's exclusivity too. The earliest mechanical point where
  implementation-not-planning manifests in the ledger is the
  submission, so admission refuses `submission.made` on a contract
  above the trivial tier whose subject stream holds no admitted
  `plan.approved`. `claim.taken` stays freely admissible on unplanned
  contracts. Nothing downstream needs its own guard: `merge.observed`
  already requires the Phase 6 verdict chain, which requires the
  submission.
- **Ordering at admission, ancestry at the verdict (review finding
  on #120).** Approval-before-submission alone would accept an
  implementation prepared *before* the plan merged and blessed after
  the fact, so the gate is two layers. Layer one, admission (this
  task): above the trivial tier `submission.made` must also carry
  `{"plan": "<path @ commit>"}` naming the approved plan anchor it
  implements — presence- and shape-checked, refused `plan_required`
  without it. Layer two, the verdict (Phase 6, already bound by the
  build plan's "receipt computation (plan hash at merge-base …)"):
  the verifier computes the plan's hash **at the submission's
  merge-base**, so an implementation whose base predates the plan
  merge carries no (or a different) plan at its merge-base and fails
  verification — the ancestry binding is exactly the receipt's job,
  and the cited anchor gives it the claimed commit to check against.
  Admission cannot do this itself (commit ancestry of the code repo
  is not a ledger fact at the admission point), so until Phase 6
  lands the ordering check plus the cited anchor is the enforced
  surface and the ancestry hole is a **named residual with its
  closing item**, not a silent gap.
- **The trivial tier is the literal tier value `"trivial"`.** 5.1
  binds `intent.filed` to carry a non-empty `tier` as presence-only
  data; the plan gate needs exactly one distinguished value now, and
  the charter's own term names it. A contract whose filed tier is
  `"trivial"` submits without a plan; every other value gates. Tier
  content semantics, qualification, and anti-gaming provenance stay
  Phase 9/10 (the recorded 5.4 posture: presence now, meaning at the
  tier phases); a filer mis-tiering to dodge planning is visible in
  the ledger and named a residual, not silently accepted.
- **Refusal is a new envelope row: exit 16 `plan_required`.** The
  stale precedent (exit 15) settled that a machine-actionable
  precondition refusal a worker responds to differently gets its own
  exit: `plan_required` sends the claimant to plan, where
  `invalid_transition` (3) means a bug and `fenced_out` (6) means a
  lost race. Spec row, constant, and the CLI parity-test row land in
  one change, per the allocation rule.
- **`plan.*` events are facts, not transitions.** The 5.1 pinned
  invariant (the four `claim.*`/`submission.made` verbs are the only
  `in_progress` exits) stands: `plan.proposed` and `plan.approved`
  change no lifecycle state and get no transitions.json rows — they
  are subject-stream facts the fold reads, exactly the standing 5.1
  treatment of `verdict.rendered`/`merge.requested` as free verbs.
  The 5.2 fold (`StateAt` returning state, anomalies, claim,
  priorClaimants) additionally tracks `planApproved` per subject: the
  position and ref of the last admitted `plan.approved`, consumed by
  the submission gate.
- **Payload shapes reuse the combined anchors.** `plan.proposed`
  carries `{"plan": "<path @ commit>"}` (the plan file on its PR
  branch); `plan.approved` carries `{"plan": "<path @ commit>",
  "pr": "<pr @ merged-commit>"}` — the 5.4 anchor forms,
  classifier-exempt like every established combined anchor.
  Admission enforces shape-level presence (non-empty, both parts of
  each anchor) per the 5.1 presence pattern; verifying that the named
  merge really happened is the same external-fact posture as
  `merge.observed`, operator-attested in v0.
- **Capability rows.** `plan.proposed` accepts {`claim`, `operator`}
  — the claim holder plans, and on a claimed subject the 5.2 citation
  matrix applies unchanged (an active fence is cited). `plan.approved`
  accepts {`operator`} only in v0, mirroring `merge.observed` (the
  observer lane arrives with Phase 6). Rows land in the
  `next/spec/actors.md` table, `keyring.AcceptedCapabilities`, and
  the spec-parsing vocabulary test, the 5.1 pattern.
- **The document lint is a pure function over one markdown file, and
  a verb.** Seed plan documents mirror the v1 shape (the fixed
  default: reuse v1 conventions where semantics match): a markdown
  file at `plans/<subject>.md` in the instantiation repo, with four
  REQUIRED non-empty sections — boundary set, retention set,
  validation commands (which must visibly cover boundary AND
  retention), expected diff shape. `next/internal/plan.Lint` returns
  every violation with the missing-retention case a distinct,
  spec-named finding (the charter singles it out); `seed plan lint
  <file>` wraps it for CI and planners. The lint reads content
  structure only — it never executes commands.
- **Structural disjointness ships as an invocable check, not just a
  function (review finding on #120).** `next/internal/plan.Classify
  (paths)` maps a changed-path set to plan | implementation | mixed:
  exactly one path, under `plans/`, is a plan PR; zero `plans/**`
  paths is an implementation PR; anything else (a mixture, or two
  plan files) is mixed. On top of it this task ships the enforcement
  entrypoint any CI invokes: `seed plan classify [paths… | -]`
  (paths as args or newline-separated on stdin, exactly the shape a
  forge's changed-files list provides), exit 0 with the class for
  plan/implementation and exit 9 `classification` refusing mixed —
  drilled against fixture path-lists including the mixed refusal, so
  the required check exists and is runnable from 5.5 on, not
  deferred as an unassigned intention. Making that check **required
  on the forge** for Seed's self-hosted deployment is then a named,
  concrete later item: the Phase 12 "protections desired-state
  reconciler" owns required-check wiring, and the spec cites it.
  (The SEED-NEXT development loop in *this* repository is already
  enforced today by v1's own `seed pr classify` in the verify
  workflow — the deployment-level wiring this bullet plans is for
  Seed's own instantiations.)
- **Sequencing.** Implements after 5.1 (admission rule set,
  transitions, capability-row machinery) and 5.2 (the fold that
  carries claim state) are on main; extends both. Independent of 5.3
  and 5.4 content except shared anchor conventions.

## Steps

1. **Spec** (`next/spec/plans.md`, new): the falsifiable-plan
   contract — four required parts, missing-retention as a named lint
   failure, the document location and section shape, the
   `plan.proposed`/`plan.approved` payload anchors, the submission
   gate above the trivial tier with the `"trivial"` literal bound,
   exit 16 `plan_required` (row also added to
   `next/spec/envelope.md`), capability rows (also
   `next/spec/actors.md`), disjointness classification, residuals
   (mis-tiering; CI wiring deferred to the port phases). Conformance
   mapping quotes the III.F row.
2. **Document lint** (`next/internal/plan`): `Lint([]byte) []Finding`
   — section presence and non-emptiness, commands section covering
   both sets, distinct finding kinds; `Classify([]string) Class` for
   the path shape.
3. **CLI** (`next/cmd/seed`): `seed plan lint <file>` rendering
   findings in the envelope (exit 0 clean, exit 9 classification on
   findings, matching the established lint-verb exit posture);
   parity-test row for exit 16.
4. **Fold + admission** (`next/internal/transition` or the fold's
   home per 5.2's landing, `next/internal/admit`): track
   `planApproved` per subject; refuse `submission.made` above the
   trivial tier without it (exit 16, error code `plan_required`,
   holder/tier/subject named in the message); shape-level payload
   presence for both `plan.*` verbs; capability rows in
   `keyring.AcceptedCapabilities`.
5. **Drills**: lint accepts a complete plan; refuses each missing
   part separately; missing retention is the distinct named finding
   (the III.F clause verbatim); commands section missing either
   set's command fails; classifier maps plan / implementation /
   mixed / two-plan-files; admission: non-trivial submission without
   plan refuses 16, with admitted `plan.approved` admits, trivial
   tier admits without plan, `plan.proposed` obeys the citation
   matrix on a claimed subject, `plan.approved` is operator-gated;
   envelope parity row; spec-parsing vocabulary test covers the new
   capability rows.
6. **Docs**: progress row, decisions entry, LEARNINGS if any.

## Acceptance Criteria

**Boundary set (new, shown working):**

- `seed plan lint` refuses a plan missing any of the four parts and
  names missing retention distinctly; accepts a complete plan.
- `Classify` returns plan / implementation / mixed per the path
  contract, drilled on all four shapes.
- `submission.made` above the trivial tier without an admitted
  `plan.approved` refuses exit 16 `plan_required`; admits with one;
  trivial tier admits without.
- `plan.proposed`/`plan.approved` payload presence and capability
  rows enforced; exit 16 parity row green.

**Retention set (existing, shown unharmed):**

- The 5.1 lifecycle drills, 5.2 fence drills, and the full admission
  suite stay green (the fold extension adds a field, changes no
  existing semantics).
- Projection, packet, and acceptance suites untouched and green.
- `make check` green at the coverage gate.

## Validation Commands

- Boundary: `cd next && go test ./internal/plan/... ./internal/admit/... ./cmd/seed/... -count=1`
- Retention: `cd next && go test ./... -count=1` and `make check`
  (exit checked separately from any pipe).
