# Plan: next Phase 3.2 — admission checks grants per verb (os-3979d48b)

Implements [`docs/next-build-plan.md`](../docs/next-build-plan.md) Phase 3
item 2: admission checks grants per verb, operator-only verbs refuse
non-operator keys structurally, and enrolled kind stays a documented
assertion nothing security-relevant reads. Design authority:
[`SEED-NEXT.md`](../SEED-NEXT.md) Part II "Capabilities" ("Grants are
events … Admission checks grants on every verb. Operator-only verbs
refuse non-operator keys structurally."). Conformance: III.E "grants are
capability data checked at admission; out-of-grant verbs are refused
structurally; operator-only verbs refuse non-operator keys" (the
no-self-approval half lands with verdict verbs, Phase 6; qualification
tuples, Phase 10). Builds on 3.1 (plan #97 / task #100): the keyring
already accumulates `actor.granted` capabilities as data, and the
interim root-only authorization this task replaces was recorded as
admission policy precisely so this change needs **no protocol bump**.

**Versioning stance (considered, held).** The bump discipline in
`next/spec/protocol.md` governs judgments about chain validity: what a
conformant validator accepts when replaying history. Authorization is
not that. Verification tolerates admission-refused conditions in
history by design — the halt gate and payload classification are both
admission-only rules that landed without bumps, and 3.1's decision log
classes the root-only rule the same way — so a 3.1 admission point and
a 3.2 admission point never disagree about whether a chain is valid;
they differ only in which proposals they accept, exactly as two builds
with different classification tables do. A deployment runs one
validator (the sole-writer hook), so evolving its admission policy is a
deployment upgrade, not a wire-protocol change; under cooperative
posture the divergence window is the posture's already-named
consequence. The alternative (a `seed/2` boundary per policy change)
was considered and declined: it would version every future policy rule
(fences in Phase 5, budgets in Phase 7) into the protocol, churning the
version register for rules verification never consults. If review
prefers the bump anyway, it is a mechanical extension of 3.1's
activation machinery — but the default this plan sets is: capability
checks are admission policy at `seed/1`.

## Steps

1. **Capability vocabulary as data.** A verb-to-accepted-capabilities
   table (each row a **set** of alternatives, any one of which admits):
   `next/spec/actors.md` gains the normative "Capabilities" section and
   `internal/keyring` mirrors it (one Go map + a spec-parity test, the
   envelope-constant discipline). v0 rows, for the verbs that exist:
   `system.halt.declared`, `system.halt.lifted` (charter: "only an
   operator's `system.halt.lifted` may append"),
   `system.protocol.upgraded`, and every `actor.*` verb accept
   **`operator`** only; `system.checkpoint` accepts **`maintenance` or
   `operator`** — the charter names checkpoints as signed by the
   maintenance actor or an operator, and folding maintenance into
   `operator` would hand the Phase 9 loop halt and actor-management
   authority it must not hold. All other verbs require active standing
   only. Later phases append rows (claim rights by squad and tier,
   verdict rights, curation-proposal rights) when their verbs land; the
   table is data, so appending rows is not a redesign.
2. **Grant resolution in the keyring.** `keyring.HasCapability(fp,
   capability)`: governance roots hold `operator` implicitly (the
   genesis trust anchor; a deployment's first grants must come from
   somewhere), enrolled actors hold exactly what `actor.granted`
   accumulated. Grant-level revocation has no catalog verb: ending an
   actor's standing (suspension/revocation) ends all its capabilities;
   finer-grained grant withdrawal is deferred until the catalog grows a
   verb for it (recorded decision).
3. **The standing rule generalizes.** The interim root-only check
   becomes: look up the verb's required capability; when one is
   required and the signer lacks it, refuse with the existing
   `OutOfGrantError` (exit 14, same meaning, message now naming the
   missing capability). `actor.*` verbs keep their `seed/1` activation
   refusal; the capability check applies wherever a keyring exists
   (at `seed/0` positions only genesis roots resolve at all, so
   operator-only holds there by construction — noted in the spec, not
   special-cased in code). Admission policy, not chain validity:
   verification keeps tolerating history, the cooperative posture's
   named consequence, unchanged from 3.1's recorded decision.
4. **Kind neutrality shown, not asserted.** The charter's
   kind-is-an-assertion language is already normative in `actors.md`;
   this task adds the behavioral pin: a drill enrolling two actors that
   differ only in `kind`, granting them identically, and asserting
   byte-identical admission outcomes across the verb vocabulary —
   nothing security-relevant branches on kind, enforced by test.
5. **Tests** (library, admission, hook, CLI): the vocabulary parity
   test (spec table == Go map); operator verbs refuse enrolled
   non-operator keys at exit 14 naming the missing capability
   (halt declare/lift, protocol upgrade, actor.*), through the rule
   set, the `seed-admit` hook, and the CLI append paths; an
   `actor.granted {"capability": "operator"}` recipient exercises
   `actor.*` and halt verbs end-to-end (delegation beyond the root
   works); ordinary verbs still need only active standing; the kind
   parity drill; retention (all prior suites unchanged, ≥90% gate).

## Acceptance Criteria

**Boundary set (new, shown working):**

- Every operator-only verb (halt declare/lift, protocol upgrade,
  `actor.*`) refuses an enrolled non-operator key at exit 14
  `out_of_grant`, with the message naming the accepted capabilities —
  through the client rule set and the pre-receive hook alike; a
  `system.checkpoint` from a key granted `maintenance` admits, while a
  key holding neither `maintenance` nor `operator` refuses.
- A key granted `operator` via `actor.granted` exercises those verbs
  without being a genesis root (delegation works; the interim
  root-only policy is fully retired).
- The verb-to-capability table in `actors.md` and the code mirror are
  pinned equal by test.
- Two actors differing only in `kind` behave identically across the
  whole vocabulary (kind is an assertion, enforced by drill).

**Retention set (existing, shown unharmed):**

- All existing verb suites pass unchanged
  (`cd next && go test ./internal/... ./cmd/... -count=1`).
- The repo-wide gate stays green with the ≥90% coverage gate
  (`make check`).
