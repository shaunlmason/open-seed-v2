## Design decisions (binding for this task)

1. **The return path is `contract.returned`** (`review` → `ready`), a
   new table row: strict payload `{"verdict": "<position>"}` citing
   the admitted **fail** verdict on the subject — a return without a
   red verdict refuses (nobody yanks an in-review contract whose
   verdict is pass or pending), and citing a pass verdict, a
   non-verdict position, or another subject's verdict refuses by
   name, the chain-citation discipline. Capability
   `{dispatch, operator}` (returning work to the queue is queue
   management, the reap posture). The cited fail verdict must itself
   pass the 6.2 verifier-boundary validation (`launderedVerdict`):
   a raw-pushed fail by an ungranted or implementing key authorizes
   nothing (review finding on this plan). The subject re-enters `ready` for a
   fresh claim → submission → verdict cycle; prior facts (verdicts,
   the sealed commitment, prior claimants) persist as history. The
   seal survives a return by design: the commitment predates the
   *first* claim, which is the proof that matters, and re-sealing
   after a return is exactly what the 6.3 window rule refuses.
2. **The lockout binds pass verdicts to unjudged submissions — and
   only authenticated fails lock.** `verdict.rendered` with
   `"verdict": "pass"` refuses — at admission (the verdict rule) and
   at `seed verdict render` (new exit **25 `red_locked`**) — while an
   admitted **fail** verdict cites the same bound submission: after a
   red verdict, pass is reachable only through a **new submission**
   (the charter's "until a new submission", by construction, since
   verdicts bind submission positions). The locking fail must itself
   satisfy the 6.2 verifier boundary (`launderedVerdict`: verdict
   grant at the tip keyring, disjoint from the implementing keys) —
   the tolerant fold records any well-shaped raw verdict, and without
   this check a raw-pushed fail by an unauthorized signer would block
   a legitimate pass, a denial of service on the pipeline (review
   finding on this plan); an unauthenticated fail locks nothing and
   authorizes nothing, and `verdict_unverified` already surfaces it
   record-side. Re-rendering **fail** on the same submission stays
   admissible (attributable, harmless, and the verifier may need to
   restate). The implementer cannot clear the lockout: the return
   path is dispatch/operator-gated, the new submission needs a fresh
   claim cycle, and L1 already keeps implementing keys out of the
   verdict lane entirely.
3. **The override is `merge.overridden`** — a fact, not a transition:
   strict payload `{"reason": "<nonempty>", "verdict": "<position>"}`
   citing an admitted, boundary-validated **fail** verdict bound to
   the current submission, admitted only on `review` subjects,
   capability `{operator}` **only** (the third no-fallback row is the
   point: the charter names it "its own attributable verb, never a
   disguised verdict" — it folds as an
   `OverrideFact{Pos, Signer, Reason, CitedVerdict}`, never as a
   verdict, and every surface shows it under its own name). The
   citation requirement is what keeps the hatch an escape and not a
   bypass (review finding on this plan): an override with no verdict,
   over a pass verdict, over a stale-submission fail, or over a
   laundered fail each refuses by name — an operator cannot route
   around independent verification wholesale, only overrule a
   standing red verdict, attributably. (The no-verifier-available
   emergency — overriding when no verdict can be rendered at all —
   stays with the halt and governance paths; deferred, recorded in
   the decision log.) An admitted override substitutes for the pass
   verdict in the chain:
   `merge.requested` may cite `{"override": "<position>"}` (mutually
   exclusive with `"verdict"`), and `merge.observed`'s chain rule
   accepts an admitted override plus a request citing it exactly as
   it accepts a pass verdict plus its citation — each step still its
   own event, nothing collapsed. The override clears the red
   lockout for the merge path (that is what an operator escape hatch
   is for) while `verdict.rendered(pass)` stays locked — the override
   substitutes for a verdict, it never manufactures one. One override
   per submission window: a second refuses; a return then a new
   submission opens a new window.
4. **Override laundering is refused up front** — the 6.2/6.3 pattern
   applied preemptively rather than waiting for review: the chain
   steps citing an override validate the override's *signer* against
   the operator boundary (tip keyring, the established v0
   approximation) and its position against the bound submission;
   `internal/reconcile` gains `VerifyOverrides` and the
   record-derivable `override_unverified` class (position-accurate
   keyring replay), beside a new `overridden` class that neutrally
   surfaces every subject whose chain ran through an override —
   "never a disguised verdict" means the report always says so.
5. **Projections surface both.** The fold gains
   `Override *OverrideFact` and contracts bump to v8 with
   `override: {position, reason} | null` (explicit null, the chain
   convention); report v5 counts `overridden` and
   `override_unverified`; cache generation 7 / version "8" with the
   override columns and the established republish drills.
6. **Specs, not new files.** `lifecycle.md` resolves the named
   extension point (the `contract.returned` row and its citation
   rule); `verdicts.md` gains the lockout and exit 25;
   `reconciliation.md` gains the override's chain semantics and the
   two classes; `actors.md` gains the `contract.returned` and
   `merge.overridden` rows. No new CLI verbs: facts append through
   the established ledger surface, and the one CLI touch is render's
   exit 25.

## Steps

1. **Table + fold.** `contract.returned` in `table.json`
   (review → ready); completeness maps `{verdict}`;
   `OverrideFact{Pos, Signer, Reason, CitedVerdict}` captured on `review` subjects
   (tolerant capture with the anomaly posture for raw pushes outside
   review or duplicate overrides in one window); the fold clears
   nothing on return (facts are history).
2. **Admission.** The return rule (state review, strict shape, cited
   position is the admitted fail verdict on this subject); the
   lockout in the verdict rule (pass over a fail-judged submission
   refuses by name); `merge.requested` extended to the
   override/verdict citation choice (exactly one; override must be
   admitted, postdate the bound submission, and satisfy the signer
   boundary); `merge.observed`'s chain rule extended to the
   override-backed path; capability rows in keyring
   (`contract.returned` → `{dispatch, operator}`,
   `merge.overridden` → `{operator}`) with the spec-parsing test
   pinned. Drills: return admits on a fail-verdicted review subject
   from dispatch and operator and refuses from claim/plain lanes,
   without a verdict, citing pass, citing another subject's verdict,
   or citing a raw laundered fail (ungranted or implementer-signed);
   pass-after-fail refuses at admission while fail-after-fail
   admits; a raw-pushed unauthenticated fail locks nothing (pass
   still admits and renders) and authorizes no return; a new
   submission after a return unlocks pass; the override admits from
   operator only over a validated fail on the current submission,
   and refuses twice in one window, outside review, with an empty
   reason, with no verdict, over a pass verdict, over a
   stale-submission fail, and over a laundered fail;
   requested-citing-override admits and citing both/neither refuses;
   observed lands done through the override chain; raw-pushed
   overrides fold tolerated with anomalies counted.
3. **Reconcile.** `VerifyOverrides` (position-accurate operator
   check) and the `overridden` + `override_unverified` classes wired
   into `Classify`, `seed reconcile`, and the report; drills induce
   each, including the laundered override (facts-complete chain over
   a raw override by an ungranted key).
4. **CLI.** Render's exit 25 `red_locked` with the refusal naming
   the fail verdict's position and the new-submission path; the
   end-to-end drill: fail verdict → render pass refuses 25 → return
   → re-claim → new submission → pass renders; the override
   end-to-end: fail verdict → `merge.overridden` (ledger append) →
   request citing it → observed → done, reconcile reporting
   `overridden` and the contracts view carrying the override fact.
5. **Projections.** Contracts v8 (`override` explicit-null), report
   v5, cache generation 7 / version "8"; republish-at-unchanged-tip
   and byte-identity drills extended.
6. **Docs.** progress.md ledger row and frontier (Phase 6 exit
   record is next); decisions.md (return-path shape, lockout
   binding, override semantics, the preemptive laundering
   treatment); LEARNINGS/DEADENDS as earned.

## Acceptance Criteria

**Boundary set (new, shown working):**

- The named extension point is resolved: `contract.returned` moves a
  fail-verdicted review subject to `ready`, refuses everywhere else
  and under every wrong citation, and a fresh claim/submission cycle
  proceeds; the sealed commitment and prior facts survive the return.
- The lockout holds end to end: pass over a fail-judged submission
  refuses at admission and at render (exit 25, naming the fail
  verdict and the path out); only a boundary-validated fail locks —
  a raw-pushed unauthenticated fail blocks nothing and authorizes
  neither a return nor an override; fail restatements admit; a new
  submission unlocks pass; the implementer holds no lane that clears
  the lockout.
- The override is attributable, gated, and complete: operator-only,
  one per submission window, reason required, and admitted only over
  a validated fail verdict on the current submission (no verdict,
  pass, stale, and laundered citations each refuse by name); the
  chain reaches done through request-citing-override with no step
  collapsed; the fold, contracts v8, and the report all show it
  under its own name (`overridden` class), and a laundered override
  surfaces `override_unverified` and refuses at the admitted chain
  steps.
- Contracts v8 / report v5 / cache generation 7 carry the override
  surface with explicit null and the republish drills green.

**Retention set (existing, shown unharmed):**

- Every pre-existing suite is green: `make check` passes at the
  coverage gate; no existing test is weakened, skipped, or deleted.
- 6.1–6.3 behavior is unchanged: exits 17–24, the verdict/chain/seal
  admission matrices, and the reconcile classes all hold as landed;
  the only new refusals are on surfaces that did not exist.
- No v1 surface changes; the task PR never touches `plans/**`.
