## What the tree actually shows

- **The audit exists as a library.** `simulate.Audit(records
  []*event.Record) AuditResult` (`internal/simulate/audit.go`): the
  five bars as evidence lists, each naming the records that violate
  it, `Clean` true when every list is empty; the transition table's
  fold for chain violations, contiguity for lost updates, the four
  deliberate exits for silent abandonment, the published offer for
  guardrail breaches, the covering reservation for unreserved spend.
  Its drills (`internal/simulate/audit_test.go`) plant each violation
  once, crafting records directly.
- **The ledger verbs read a directory.** `runLedgerVerify`
  (`cmd/seed/ledger.go`) opens the store, bootstraps genesis,
  verifies from genesis with the build's supported versions, and
  renders a tip-stamped envelope; a verification failure renders the
  `chain_invalid` envelope with the failing position. `Store.Records`
  walks the records in position order.
- **The vocabulary is one table.** `cmd/seed/catalog.go` registers
  `ledger` with subverbs `verify`, `append`, `show`;
  `TestRegistryMirrorsTheCLIVocabulary` holds the registry to the
  group's own usage message ("ledger requires a subverb: verify,
  append, or show") both ways, and `seed serve` draws its method set
  from the registry, so a subverb added to both places is on the
  machine-protocol surface with no further change.
- **No exit code says "the history breaks a bar".** `chain_invalid`
  (8) is verification failing; `drift` (28) is a declared desired
  state differing from an observed one, refined today by
  `protections_drift`, `preseed_drift` and `docs_drift`. A bar is a
  declared invariant the chain is held to, and a violated bar is the
  observed chain differing from it.

## Design decisions (binding for this task)

- **D1 — verify first, audit the records verification saw.** `seed
  ledger audit --ledger <dir> [--supported <versions>]` runs exactly
  `ledger verify`'s prologue: open, bootstrap, verify from genesis; an
  invalid chain refuses with the verify verb's own `chain_invalid`
  envelope before the audit reads anything, because a bar over an
  unverified chain is a bar over nothing. The records audited are the
  ones the verification replay observed (`ledger.WithObserver` on
  `VerifyFromGenesis`), never a second scan of the directory: a
  writer appending between the replay and a rescan would hand the
  audit records the report's count and tip do not cover, and the
  envelope's position must name the chain the bars were read from.
- **D2 — one envelope, the bars as they are.** The result carries the
  `AuditResult` fields verbatim (`chain_violations`, `lost_updates`,
  `silent_abandonments`, `guardrail_breaches`, `unreserved_spend`,
  `clean`) plus `count` and `tip`, stamped at the tip audited like
  `verify`'s envelope. A clean audit exits 0. A violated audit refuses
  with exit 28 `drift` refined `audit_violated`; `result` and `error`
  are exclusive under `seed-envelope/0`, so the lists ride the
  message, deterministically: each violated bar named with the
  records it names, in the bars' fixed order (`silent_abandonments
  [c-1]; unreserved_spend [c-2]`), so a reader has the lists without
  a second call and no envelope version moves; the refinement row
  lands in `envelope.md`'s table, no new exit number.
- **D3 — the subverb is in both places the vocabulary lives.** The
  registry's `ledger` group gains `audit` and the group's usage
  message says "verify, append, show, or audit", so the registry
  drill and `seed serve --list` agree without a special case.
- **D4 — drilled through the CLI over a real ledger.** A CLI drill
  builds a ledger with the test keys the ledger drills already use,
  appends a clean happy path and audits it clean; then plants each of
  the four plantable violations (an unclosed window, an unreserved
  run, an unoffered claim, and a chain violation raw-appended past
  admission the way the audit drills craft one) into its own ledger
  and asserts the refusal names that bar and the envelope carries the
  record. The lost-updates bar (an empty chain) cannot be reached
  through the verb: a ledger with no genesis fails verification
  first, which is D1 working as intended, and the drill says so by
  asserting `chain_invalid` there. The invalid-chain refusal (a
  corrupted segment) exits `chain_invalid` with no audit fields. `seed serve` returns the same envelope for
  the `ledger.audit` method (the existing byte-identical corpus
  drill extended by one entry).
- **D5 — bounds.** No admission change, no projection, no change to
  `simulate.Audit`'s bars or the simulation; `simulation.md` gains
  the sentence that the same audit runs over any ledger through the
  verb, `promotion.md`'s protocol drops its "today reachable only
  through seed simulate" clause, and the packet's citation drill
  keeps holding.

## Acceptance Criteria

**Boundary set (new, shown working):**

1. **A clean ledger audits clean.** `seed ledger audit --ledger <dir>`
   over a verified happy path exits 0 with every list empty, `clean`
   true, stamped at the tip.
2. **Each bar refuses by name.** Each planted violation exits 28
   `audit_violated`, the message naming the bar and the result
   carrying the record; a ledger with no genesis refuses
   `chain_invalid` before any bar is read.

   `chain_invalid` at the failing position with no audit fields.

   corpus returns the CLI's envelope byte for byte for `ledger.audit`.

   carries `audit_violated` under 28, and the emitted-codes drill
   passes.
6. `make check` green; no model identifiers in any committed
   artifact.
