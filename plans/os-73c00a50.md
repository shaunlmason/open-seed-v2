# Plan: next Phase 5.4 — the acceptance-spec field and the spec gate (os-73c00a50)

Implements [`docs/next-build-plan.md`](../docs/next-build-plan.md) Phase 5
item 4: "Acceptance-spec field on contracts; the spec-gate flag
(executable content requires a gate event before any run) — enforcement
lands with verdicts (Phase 6)." Design authority:
[`SEED-NEXT.md`](../SEED-NEXT.md) Part II §6 "Acceptance specs are
privileged code (normative)" (a spec ultimately causes command
execution on a verifier; spec authorship above the trivial tier passes
the same review gate as code; a mirror-derived intent can *propose*
acceptance content but it becomes executable only through that gate; no
text from outside the trust boundary becomes an executed command
without a gate between) and conformance III.F rows 1–2 ("A contract
cannot leave draft without an acceptance spec; the spec's executable
content passes a review gate before it can run anywhere; specs are
protected artifacts" and "Text originating outside the trust boundary
can propose but never directly become executable acceptance content;
the gate between is structural and tested against a hostile corpus").
Deps: the 5.1 plan (#113 — `contract.specified` carries the acceptance
presence rule this task deepens); implementation stacks on the Phase 5
chain.

## Design decisions (binding for this task)

- **The acceptance spec is a repo artifact, referenced — never inline
  prose that executes.** The charter's gate is "the same review gate
  as code", which means the spec body lives in the repository and
  merges through a PR like everything else; the contract carries a
  commit-anchored reference. `contract.specified`'s payload deepens
  from 5.1's presence rule to the structured field:
  `{"acceptance": {"ref": "<path @ commit>", "executable": bool,
  "gate": "<pr @ merged-commit>"}}` — `ref` uses the established
  combined anchor form (classifier-exempt), `executable` declares
  whether the spec body contains runnable content, and `gate` is the
  review-gate evidence (present iff required).
- **The spec-gate flag is a structural shape rule at
  `contract.specified`, with NO tier exemption**: `executable: true`
  REQUIRES `gate`, at every tier (review finding on #116: the
  charter's "above the trivial tier" clause relieves *authorship
  review process*, but its "no text from outside the trust boundary
  becomes an executed command without a gate between" carries no
  tier exception — and without origin provenance, a trivial contract
  spawned from a `request.*` proposal would let a dispatcher copy
  outside text into the referenced artifact and arm it gateless).
  Requiring the gate universally is stricter than the charter and
  therefore safe; the future relaxation for trusted-authored
  trivial-tier specs is named as requiring real origin provenance
  and lands with the tier system (Phase 9/10), never before.
  `executable: false` (prose-only criteria) needs no gate. What 5.4
  can enforce is exactly this **gate-before-specified** half; the
  **gate-before-run** half is the verifier's refusal to execute
  ungated content and lands with verdicts (Phase 6), stated plainly
  in the spec so the split is honest.
- **Gate evidence is bound to the acceptance revision** (review
  finding on #116: two independent anchors would let any unrelated
  merged PR vouch for an unreviewed spec): the commit in
  `acceptance.ref` MUST equal the merged commit in `gate` — the spec
  is referenced exactly at the gate PR's merge commit — checkable as
  string equality at shape level with no repository access, and
  exactly what the deferred forge reconciliation later re-verifies
  against forge fact. A mismatch refuses naming both commits.
- **Outside text can propose, never arm** (III.F row 2, structural):
  the catalog's `request.*` events are the inbound-proposal surface;
  a request event may carry proposed acceptance *prose*, but nothing
  in the schema lets a request payload carry `executable: true`
  content or a `gate` field — proposals are data by construction,
  and only a `dispatch`/`operator`-capable actor's
  `contract.specified` with gate evidence arms executable content.
  The hostile corpus extends: a request-origin payload smuggling
  gate fields or executable markers refuses; imperative prose in
  proposals stays under the classification budget.
- **The derived flag is visible**: the contracts view's entries gain
  `acceptance: {ref, executable, gated}` (gated = gate evidence
  present or not required), so "may this spec run?" is a projection
  read, Phase 6's verifier consumes it, and staleness rules already
  apply. Contracts view Version bumps.
- **`gate` evidence is an observation, not a verdict**: `"pr @
  merged-commit"` cites forge fact the way `plan.approved` does
  (observation of a merge). v0 validates its shape (combined anchor
  form); reconciling it against the forge (divergence detection) is
  Phase 6/8 observation machinery, named as the extension point.
- **No new exit codes**: gate violations are shape refusals;
  classification keeps exit 9.

## Steps

1. **Schema** (`next/internal/transition` or the packet-adjacent
   spec seam, wherever 5.1 lands the specified-payload check): the
   structured acceptance field with strict keys; the
   gate-required-when-executable rule and the ref/gate commit
   equality; combined-anchor validation for `ref` and `gate`.
2. **Admission wiring** (`internal/admit`): `contract.specified`'s
   presence check (5.1) deepens to the structured rule; refusals name
   the missing piece (`acceptance.ref`, `acceptance.gate`); request
   events structurally cannot carry the executable/gate keys
   (unknown-key strictness on the request-proposal shape).
3. **Projections** (`internal/project`): contracts entries gain
   `acceptance: {ref, executable, gated}`; version bump; queue
   unchanged (readiness already implies specified).
4. **Spec** (`next/spec/lifecycle.md` + `next/spec/contracts.md` or a
   new `next/spec/acceptance.md`): the privileged-code posture
   verbatim, the field schema, the universal gate rule with the
   provenance-gated Phase 9/10 relaxation named, the ref/gate
   revision binding, the gate-before-specified vs gate-before-run
   split with Phase 6 named, the propose-vs-arm boundary, and the
   conformance mapping for III.F rows 1–2 (row 1's "before it can run
   anywhere" explicitly carried by Phase 6).
5. **Drills**:
   - *Shape*: executable-without-gate refuses at every tier, the
     trivial tier included; prose-only admits gateless at any tier;
     a `gate` whose merged commit differs from the `ref` commit
     refuses naming both; malformed `ref`/`gate` anchors refuse;
     unknown keys refuse.
   - *Propose-vs-arm* (the III.F row 2 structural test): a request
     event carrying proposed prose admits as data; the same payload
     with `executable: true` or a `gate` key refuses at shape; the
     hostile corpus gains rows for gate-field smuggling and
     imperative-prose proposals over budget.
   - *End-to-end*: filed → specified-with-gated-executable-spec →
     claimable; the contracts view shows `{ref, executable, gated}`
     and the version bump republishes at an unchanged tip.
   - *Tolerant history*: raw-pushed ungated-executable history
     verifies (admission policy) and surfaces as anomalies.

## Acceptance Criteria

**Boundary set (new, shown working):**

- `contract.specified` enforces the structured acceptance field:
  commit-anchored `ref`, the executable flag, gate evidence for ALL
  executable content, and ref/gate commit equality; every planted
  violation refuses naming the missing or mismatched piece.
- A request-origin payload structurally cannot arm executable
  content: the executable/gate keys refuse on the proposal shape,
  drilled against hostile-corpus rows including gate-field smuggling.
- The contracts view carries `acceptance: {ref, executable, gated}`
  and republishes under a new version-bearing build id at an
  unchanged tip.
- Raw-pushed ungated-executable history verifies and surfaces as
  anomalies; the spec states the gate-before-run half lands with
  Phase 6's verifier.

**Retention set (existing, shown unharmed):**

- All existing verb suites pass unchanged
  (`cd next && go test ./internal/... ./cmd/... -count=1`).
- The repo-wide gate stays green with the ≥90% coverage gate
  (`make check`).
