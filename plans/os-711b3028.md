# Plan: next — the client's private git dir arms auto-gc in production (os-711b3028)

The card, filed from a review finding on #184 and deliberately excluded
from os-c4e8b57a (that plan's D4: "no production change"): *"gitref.
NewClient inits a private bare git dir at `<stateDir>/gitdir` and
writes no config, so outside a test binary that repository runs under
stock git auto-gc. The dir is client-owned, ephemeral transport state:
a detached gc mutating it after the CLI has exited serves nobody, and
a caller that removes its state dir (a CI job cleaning a workspace)
hits the same unlinkat-directory-not-empty failure the drills hit."*
Its question: whether `NewClient` should write `gc.auto=0`,
`gc.autoDetach=false` and `receive.autoGC=false` into the git dir it
creates, at init, before its first object; and its named consequence:
`TestClientGitDirHasNoAutoGC` can then assert the repository-local
property rather than the effective one, which is what the review asked
for.

## What the tree actually shows

Measured, not assumed:

- **Two production sites create git repositories, not one.**
  `gitref.NewClient` inits the bare private git dir once and reuses it
  across invocations; `verdict.NewWorkspace` clones a per-run
  repository (`--no-checkout --no-hardlinks`), checks out the head, and
  `Cleanup` removes it pass or fail. Neither writes any git config.
  `git gc --auto` fires after fetches and receives (the client's every
  round trip) and after checkouts of a clone; `gc.autoDetach` is the
  default, so the collector outlives the process that armed it.
- **Every TEST repository is hardened; production is not.**
  os-c4e8b57a's `hardenGitRepo` writes the three keys into every
  fixture repository, the gitref package's `TestMain` points
  `GIT_CONFIG_GLOBAL` at a config carrying them for every git process
  the test binary spawns, and a guard refuses a test that inits a
  repository without hardening. `TestClientGitDirHasNoAutoGC` asserts
  the keys with `git config --get`, the EFFECTIVE value, which the
  process-wide global satisfies whether or not the repository carries
  them: the drill passes today for the wrong reason.
- **A state dir outlives a build.** `--state` is the client's persisted
  verified head and its git dir; a deployment that upgrades the CLI
  keeps the dir, so a write made only at `init` would never reach a dir
  an older build created.
- **No production failure has been observed**, only the test-side one;
  the card says so, and this plan does not claim otherwise.

## Design decisions (binding for this task)

- **D1 — `NewClient` configures the git dir on every construction, not
  only at init.** After the init (or the stat that finds an existing
  dir), `NewClient` writes the three keys with `git --git-dir <dir>
  config <key> <value>`, idempotently, before any fetch. A dir an older
  build created is hardened the first time a new build opens it. A
  config write that fails is `NewClient`'s error: a git that cannot
  configure its own repository cannot be trusted to fetch from it
  either, and the refusal names the key.

  Refused: writing only when absent. Three `git config` invocations
  per construction cost less than one stat-and-branch and cannot drift
  from what the drill asserts. Refused: a `GIT_CONFIG_GLOBAL` in
  production. The client's git dir is the client's; the invoking
  process's global config is the operator's, and the engine writes
  nothing there.

- **D2 — the verifier workspace gets the same three keys, derived from
  the tree.** The card names one site; the tree has two, and the
  workspace is the one whose `Cleanup` runs immediately after the
  commands that arm the collector, which is exactly the race the
  drills hit under `t.TempDir`. `NewWorkspace` writes the keys into the
  clone right after `clone`, before `checkout`. Same posture as the
  tier card counting its authority sites from the tree rather than the
  card.

- **D3 — the drills assert the repository-local property.**
  `TestClientGitDirHasNoAutoGC` queries `git config --local` in the
  client's git dir, which the process-wide global cannot satisfy; a
  sibling drill inits a bare dir with no config, points `NewClient` at
  it, and asserts the keys land (the older-build state dir); a
  workspace drill asserts `--local` in the clone. The test-side
  hardening of os-c4e8b57a stays as it is: it covers the fixtures and
  the guard, and a belt over braces costs nothing.

- **D4 — two spec sentences, no new surface.** `verdicts.md`'s
  workspace paragraph and `protocol.md`'s storage reference each gain
  one sentence: the repositories the engine creates for itself carry
  auto-gc disabled, so nothing the engine made mutates after the
  engine exits.

- **D5 — scope guard.** No other git configuration, no change to
  fetch, push, clone or checkout arguments, no `gc` invocation of any
  kind, no change to the test-side hardening or the fixture guard, no
  CLI flag.

## Acceptance Criteria

**Boundary set (new, shown working):**

1. After `NewClient`, `git config --local` in the client's git dir
   reports `gc.auto=0`, `gc.autoDetach=false`, `receive.autoGC=false`,
   asserted repository-locally so the test binary's global config
   cannot satisfy it.
2. A bare git dir created without the keys (an older build's state
   dir) carries them after `NewClient` opens it, and a second
   `NewClient` on the same dir changes nothing.
3. After `NewWorkspace`, `git config --local` in the clone reports the
   three keys; the workspace's existing drills (isolation, hard-link
   refusal, cleanup on both paths) are unchanged.
4. **Mutation evidence.** Each must fail a drill: `NewClient` skipping
   the write; the write made only inside the init branch; any one key
   dropped from the client's write; `NewWorkspace` skipping the write.
5. `make check` green with coverage measured **cold**, at least three
   readings above the gate, and the suites pass **unprivileged** under
   `setpriv --reuid=65534`.

**Retention set (existing, shown unharmed):**

- Every gitref drill (fetch, push, monotonic head, race storm,
  materialize) and every verdict drill keeps its assertions and timing;
  the fixture guard and `TestMain`'s hardening are untouched.
- No fetch, push, clone or checkout argument changes; the receipt's
  canonical bytes are unchanged for every fixture.
- No CLI flag, exit code or spec section is added.
